# 현업 워크플로우 — 큐시트는 어떻게 쓰이고, 왜 검증되지 않는가

STANDBY의 포지셔닝 근거. 출처는 문서 말미.

---

## 1. 큐시트는 한 장이 아니다

현업의 문서 생태계는 최소 5종이 병존한다.

| 문서 | 소유자 | 성격 |
|---|---|---|
| **프롬프트북 / 콜링 스크립트** | 무대감독(DSM) | 대본 좌측 + 우측 여백에 큐 표기. **콜링의 원본** |
| **마스터 큐시트** | 무대감독 | 전 부서 큐를 한 표에 모은 것 ← **레퍼런스 시트가 이것** |
| **부서별 큐시트** | 조명·음향·소품 오퍼 | 마스터에서 자기 열만 뽑아낸 것 |
| **런시트 / 진행표** | 스태프 | 큐가 아닌 작업(전환, 이동) |
| **프리셋 리스트 / 코스튬 플롯** | 소품·의상팀 | 시작 시점 상태와 환복 계획 |

이들은 **같은 사실을 다르게 적은 사본**이다.
하나가 바뀌면 나머지가 어긋난다. 우리가 조사한 소극장 워크플로우 범위에서는
**이 사본 차이를 자동 대조하는 장치를 확인하지 못했다.** 문제 가설의 뿌리가 여기다.

## 2. 작성 타임라인

```
연습실        → 페이퍼 테크    → 드라이 테크   → 큐투큐(Q2Q)  → 테크 → 드레스 → 공연
동선·대사 기록   큐 위치 합의     배우 없이       큐에서 큐로 점프   전체    전체    본번
(연필로)        · 번호 부여      기계만 돌림     (대사 건너뜀)
```

- **페이퍼 테크** — 연출·디자이너·무대감독이 앉아 대본을 훑으며 큐 위치를 정하고 번호를 붙인다.
  **극장에 들어가기 전, 종이 위에서 하는 유일한 사전 검토.**
- **큐투큐** — 큐 직전으로 점프 → 실행 → 다음 큐로 점프. 대사는 건너뛴다. 오직 큐만 검사한다.
- 이 전 과정에서 큐시트는 **계속 수정된다.** 최종본은 공연 전날 확정 → 인쇄 배포 + 공유 드라이브 업로드.

## 3. 콜링 프로토콜

무대감독은 SM 데스크에서 인터컴으로 콜한다. 큐 하나는 3부분이다.

| 요소 | 내용 |
|---|---|
| **Preface** | 대상과 번호 — `LX 45` |
| **Trigger** | 실행 시점이 되는 대사·음·동작 |
| **Action** | `GO` |

```
"Standby LX 45, Sound 12, Fly 3"      ← 예고 (수 초 전, 여러 부서를 묶어서)
    … (trigger 대사) …
"LX 45 … GO"                           ← 실행
```

약어: `LX`(조명) `SD`(음향) `Fly`(플라이) `Auto`(무대 자동화).
무대감독은 **3초 안에 판단**해야 하므로 작품을 통째로 외우고 있어야 한다.

팀 구성은 보통 3~4인: **PSM**(제작무대감독) / **SM** / **DSM**(부무대감독, 실제 콜링) / **ASM**(조감독).
프롬프트북을 들고 콜하는 사람을 영미권에서는 *"on the book"*이라 부른다.

## 4. 핵심 발견 — 정적 검증이 존재하지 않는다

> **공연계에는 리허설이라는 런타임 테스트만 있고, 컴파일러가 없다.**

- 페이퍼 테크가 유일한 사전 검토지만 **사람이 눈으로 읽는 회의**다.
  마이크 on/off 균형이나 소품 반출입 정합성을 표 전체에 걸쳐 추적하지 않는다 —
  **사람이 49행 × 17열의 상태머신을 머리로 돌릴 수 없기 때문이다.**
- 나머지는 전부 **돌려보고 터지면 고치는 방식**이다. 드라이 테크·큐투큐·테크·드레스가 전부 그것.
- 결함은 **실행되어야만 발견된다.** 마루가방이 안 나와 있는 건 그 씬을 돌려봐야 안다.

**그리고 리허설 시간은 유한하고 비싸다.**
프로도 테크 기간이 며칠이고, 대학 동아리·소극장은 **극장 대관이 2~3일**이다.
런타임 테스트 예산 자체가 부족한데, 정적 검사가 없으니 결함이 무대 위에서 발견된다.

## 5. 우리의 좌표 — 저작 도구가 아니라 린터

| 도구 | 성격 | 요구사항 |
|---|---|---|
| **Stage Write** (브로드웨이 100+ 작품, 10만 사용자) | 동선·스테이징 저작 | **자기 툴로 이주** |
| **Propared** | 프로덕션 일정 관리 | **자기 툴로 이주** |
| **Rundown Studio** 등 | 런오브쇼 저작 | **자기 툴로 이주** |
| **STANDBY** | **기존 문서 검증** | **아무것도 안 바꿔도 됨** |

조사한 대표 도구들은 저작·운영을 중심으로 설명하며 자체 workflow 사용을 전제로 한다.
STANDBY의 차별점 가설은 기존 PDF·사진을 그대로 받아 **문서 간 변경 검토만 덧붙이는 것**이다.
동일 기능을 제공하는 경쟁 제품이 없는지는 발표 전 추가 검증해야 한다.

> ⚠️ **정직하게**: 숙련된 무대감독은 엑셀 시트 링크로 부서별 뷰를 이미 자동화한다.
> 그러니 **"부서별 큐시트 생성"은 방어 가능한 핵심 가치가 아니다.** 방어선은 검증 하나다.

## 6. 왜 엑셀이 살아남는가

전용 SaaS가 있는데도 현장이 스프레드시트를 못 놓는 이유:

1. **이미 안다** — 추가 학습이 필요 없다
2. **유연하다** — 작품마다 다른 열 구성을 즉석에서 만든다
3. **연결된다** — 시트 링크로 마스터 → 부서별 자동 반영이 가능하다
4. **공짜다** — 대학 동아리 예산은 0원이다

**따라서 "엑셀을 버리게 하는 제품"은 실패한다. "엑셀을 그대로 먹는 제품"이 이긴다.**

## 7. 타깃 재조정

| | 프로 프로덕션 | **대학 동아리 · 소극장** |
|---|---|---|
| 인력 | PSM/SM/DSM/ASM 3~4인 | **1인이 전부** |
| 경험 | 작품 수십 편 | **첫 작품인 경우 다수** |
| 테크 기간 | 수일 | **대관 2~3일** |
| 예산 | 전용 툴 구매 가능 | **0원, 엑셀뿐** |

**결함이 가장 많이 나고, 잡을 시간이 가장 없고, 도구가 전혀 없는 쪽**이 명확히 후자다.

## 8. 레퍼런스 시트에서 관찰된 작성 관행

**행 문법** — `S#n`(씬) / `N#n`(넘버)이 적힌 행은 장면이고, **0열이 빈 행은 전환(암전) 구간**이다.
총 13넘버 + 17씬 + 전환행으로 구성된다.

**전환행이 가장 위험하다.** 부서 동시 관여 수가 여기서 최대가 된다 —
장면은 한두 부서가 움직이지만, 전환은 어두운 무대에서 전 부서가 동시에 움직이기 때문이다.
`43행 긴 암전 S#16`이 11개 부서로 최대치다. → [FINDINGS.md](FINDINGS.md) 참조
